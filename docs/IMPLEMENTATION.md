# Development implementation

The repository is public. The Android and Mac applications implement nearby and optional owner-hosted internet transports, with automated protocol/state tests and native build checks. They have not completed the physical-device checklist. These are development builds, and the new protocol has not received an independent security audit.

## Present in the source

- Native Kotlin/Compose Android app named **Keepresso Mobile**, original Keepresso launcher/cup artwork, copper theme, Status/Activity/Settings, two-row Mac readings, manual duration stepper, capability-aware controls and trigger timestamp and **Check** on the **Active triggers** row.
- Swift background Mac companion with a Finder/launcher settings window, no menu bar icon, with a locally initiated five-minute invitation QR, named-phone approval, saved authorization and revocation. Closing the window keeps it running invisibly; explicit Quit stops it. Automatic startup registers the bundled agent and repairs a positively identified stale registration in one bounded sequence per foreground process; macOS retains approval control. A revoked/required approval is never removed/reregistered to evade it. Settings show a warning and **Open Login Items…** when blocked. Connections and reminders run only while native Keepresso is open. It does not modify or launch the official Keepresso app.
- Mutual authentication, separate encrypted directions, bounded BLE records/queues, strict sequence checks and fresh request expiry. Credentials use Mac Keychain and Android Keystore wrapping. A durable mutation journal reserves IDs before effects; uncertain commands are not replayed automatically.
- Mac 0.4.3 keeps pairing in one section with two contextual button positions. Before saved keys load, the first action is **Unlock saved pairing…**; otherwise **Show pairing QR code** is enabled only without a paired phone. **Delete pairing** is enabled only with a loaded pairing, asks confirmation and uses durable revocation for nearby/internet access. Legacy multiple-phone records remain readable and the confirmation identifies that all are affected. New local pairing exposes a single slot. Saved credentials load off the main thread; failed/denied reads preserve keys and disable new pairing/control.
- Ordinary native session status, lock/display/lid/battery/charging, CPU Celsius and thermal-pressure readings. Unavailable or stale information remains distinguishable. An authenticated, fresh response is required before controls are enabled.
- Bounded trigger assessment using the unchanged pinned KeepressoCore in a separate worker. It uses disposable hook copies, preserves input uncertainty and runs only when the user selects Check. Current positive evidence is useful; unaudited negative reads remain unknown. A fresh partial assessment receives its own timestamp and unknown row indicators. A failed refresh retains the previous timestamp.
- Public Keepresso manual Start/Stop requests with observed-state acknowledgement. Pause/Resume uses an exact, uniquely exposed enabled Accessibility control when available; otherwise it is disabled. Stock manual/trigger semantics remain unchanged.
- Hourly/2-hour/off routine reminder policy, OK without moving the cadence, 6-hour routine-only snooze, resume, stopped-but-awake warning with 2/5/10-minute delay, thermal warnings, failed sleep requests and one lid-close warning while system sleep is disabled. That closure also requests one Mac sound and best-effort trackpad feedback. Urgent Android warnings use an alarm-audio/vibration channel; user-granted DND access can enable its exception. No volume or global DND changes are made. Sleep and unknown restart gaps cancel ambiguous stopped-session warnings. Android notification actions require a reachable authenticated Mac; they do not queue a future power action.
- Optional nearby-first internet fallback using the existing pairing, direction-separated encrypted envelopes, pre-database access tickets, fresh Mac epochs and status round-trip gating. Mutation uncertainty survives Android restart; fresh read-only journal queries reconcile it without retransmission. Reminder outbox and phone event claims survive reconnect/restart. FCM uses encrypted data messages and expiring push leases; background fetches use bounded jobs. See [SELF_HOSTING.md](SELF_HOSTING.md) for service setup and budget assumptions.

## Limitations that matter

| Area | Current behavior |
| --- | --- |
| Distance | Nearby Bluetooth, or internet when the owner has configured and verified their relay and Firebase project. Physical handoff and locked-phone delivery remain acceptance work. |
| Sleep now | Stops/pauses native holds, verifies release including Only while brewing, then requests normal system sleep once. A manually latched global override must be released on the Mac. Accepted requests do not prove completed sleep; physical owner test pending. |
| Pause/Resume | Requires Accessibility permission and an unambiguous exposed native control in the supported app version. It may be unavailable when the native menu is not exposed or localized differently. |
| Temperature | Hottest readable CPU SMC sensor, bounded and cached. A live read returned 68.3°C; unavailable reads stay unknown. Colour reflects macOS thermal pressure, which is not a fixed Celsius threshold. |
| Display dimming | Public readings distinguish on/off where possible. Dimmed is not inferred. |
| Battery safety pause | The native aggregate does not export trustworthy pause provenance. The original low-battery artwork is included, but percentage alone does not activate that icon. Battery-pause warnings are not produced from an invented provenance. Failed explicit sleep requests produce a warning. |
| Trigger negatives | Some upstream readers turn input errors into false. The companion conservatively keeps those negatives unknown until error-aware boundaries are verified. A grace-only hold never promises that native Resume will keep the Mac awake. |
| Updates | Observer compatibility is pinned to Keepresso 1.27.0. Official app updates continue independently; unsupported versions/settings disable assessment rather than silently using default rules. |
| Background delivery | Nearby uses a visible connected-device service; internet uses Firebase Messaging and bounded WorkManager tasks. Screen-off/Doze, Google Play services, vendor battery policy, Bluetooth range, Mac lid and sleep behavior require real-device testing. |
| Distribution | Development APK and ad-hoc Mac bundle. No Play Store release, notarization or unattended installation. |

The key next acceptance step is to pair the actual Android phone and Mac, inspect read-only status first, and then deliberately test commands and background reminders. Follow [ACCEPTANCE.md](ACCEPTANCE.md); no successful build or simulated acknowledgement substitutes for those observations.

## Internet-status update — installed owner trial

Mac 0.4.4 (8) and Android 0.4.1 (6) add one compact Internet / Wi-Fi-or-Network facts row. This is independent of Bluetooth transport. A fresh, credential-free HTTPS check is required for Online; no route is Offline; both public endpoint checks failing is Check failed, rather than a claim that every internet destination is down. Optional Wi-Fi name access requests macOS Location authorization only from the settings button. See [protocol](protocol.md) and [recovery](RECOVERY.md) for refresh timing, privacy and setup.

Verification on 24 October: 104 Swift, 68 Kotlin core and 18 relay tests passed; Android built and lint completed with no errors (existing warnings remain). Eight new internet dashboard cases plus six existing dashboard/settings cases passed in each of light and dark mode on the dedicated emulator. Cases include route loss with associated Wi-Fi, failed proof, checking/hidden SSID, long names/Ethernet, old helper fields, stale/future/extreme timestamps and unreachable controls. One fresh review found a potential extreme-timestamp overflow; a failing emulator regression reproduced it, and comparison against an Instant window fixed it. No review findings were deferred.

A bounded read-only diagnostic on the actual Mac returned Online / Wi-Fi, with no SSID supplied by macOS. It did not request permission or create the app model, transports, login item or power controls. Live network disruption/captive portals, actual permission-dialog behavior after consent, installed-device acceptance and live timeout/cancellation delivery remain unverified. HTTP failure/fallback responses and obsolete check tokens were tested with controlled fixtures. No hardware acceptance is inferred from these tests.

The owner explicitly approved installation with “Go” on 24 October. The canonical Mac app was updated after graceful Quit to 0.4.4 (8), and the selected Samsung was updated in place to Android 0.4.1 (6). Versions, signatures, unchanged connection choices and byte-identical wrapped phone pairing were verified. macOS is running build 8 under its registered background agent, with the installed executable fingerprint matching. The official Keepresso executable and all 107 pinned source files are unchanged. The previous companion is retained in Trash and no loose staged app remains.

The Mac settings show that this locally signed update needs the owner to use **Unlock saved pairing…** and handle Keychain before connections resume. The phone was dozing during the initial dashboard check; owner unlock/open is pending. No Keychain/Location approval was granted by the agent, pairing was not reset, and installed-device connection acceptance is not yet claimed. Optional **Allow Wi-Fi name…** remains an owner action.
