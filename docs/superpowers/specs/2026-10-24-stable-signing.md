# Stable local signing

Owner reported four password dialogs during saved-pairing unlock after Mac 0.4.4. OS logs confirm two existing items each requested decrypt authorization (24), followed by partition authorization (65538), all in the same managed process. The old ACLs pin prior build hashes; the current ad-hoc designated requirement pins a different hash. This is not evidence of four concurrent loaders. No valid local signing identity is available.

Keep the current working app, pairing, credential store and Keychain ACLs unchanged. Prepare packaging support for an explicitly selected Apple development/distribution or Developer ID certificate, identified by its exact 40-hex SHA-1 fingerprint. Stable owner builds must reject missing/ad-hoc identity, failed signing, wrong certificate/bundle identifier, unsupported certificate chain, or a resulting build-hash-based designated requirement. Apple securityd assigns a stable team partition to supported Apple-issued certificates, while self-signed identities still fall back to the build hash; a self-signed certificate cannot be claimed to fix the whole issue. Public development CI can still build ad-hoc fixtures; those do not establish durable Keychain trust.

Do not create/import a production signing key, alter certificate trust, reinstall another ad-hoc owner build, combine/delete credentials, or broaden existing Keychain access in this task. Provisioning a new persistent owner identity is a separate security-sensitive action requiring owner authorization. The switch can require a final owner Keychain approval; stable signing does not promise zero prompts when Keychain itself is locked or consent is revoked.
